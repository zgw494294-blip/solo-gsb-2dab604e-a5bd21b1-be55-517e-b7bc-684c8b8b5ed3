# 列车换乘规划

基于 **Flask + SQLite + 原生 JavaScript** 的列车换乘规划 Web 应用：导入 JSON 时刻表，查询满足换乘时间约束的**最早到达**行程，为调度员提供**单站站台分配**、**单线区间冲突排查**，根据所选班次规划**车底接续**（最少需要多少组可互换车底），按班次席位数测算时间窗内的**限座旅客疏运**最大人数（席位可复用、可分多行程送达），对晚点班次做**区间延误传播排程**（首发延误沿班次与单线区间传播后的逐项最早可行排程），并对排程结果做**晚点来源追踪**（回溯每个晚点班次末到时刻的全部根源与传导链）。

## 快速开始

```bash
docker compose up --build
```

然后浏览器访问 **http://localhost:8000** ，页面依次提供「查询行程」「站台分配」「单线区间冲突排查」「车底接续规划」「限座旅客疏运测算」「**区间延误传播排程**」等卡片入口。

（使用旧版 Compose 时命令为 `docker-compose up --build`。）

首次启动时若数据库为空，会自动导入 `sample_data/timetable.json` 示例数据，打开页面即可直接查询。SQLite 数据保存在名为 `timetable-data` 的卷中，重启不丢失。

## 本地开发

```bash
pip install -r requirements.txt
python app.py          # 访问 http://localhost:8000
```

运行测试：

```bash
pip install -r requirements-dev.txt
pytest
```

## 功能

- **导入 JSON 时刻表**：站点（ID、换乘分钟数）+ 班次（ID、按序停靠的站点与到发时间）
  - 时间格式为 `YYYY-MM-DDTHH:MM`
  - 校验：站点引用必须已定义、时间格式与取值合法、站内发车不早于到达、站间时序递增
  - 任一校验失败则整体拒绝导入，**保留旧时刻表**（先校验后写库，写库在单个事务中，失败回滚）
- **查询最早到达行程**：选择起点、终点和最早出发时间
  - 首班发车不得早于所选时间
  - 换车须满足换乘站的最短换乘分钟数（发车 ≥ 到达 + 换乘分钟）
  - 同班次经停无需换乘
  - 时间含日期，跨午夜按日期自然计算
  - 到达时间相同时，依次选择换乘次数更少、班次 ID 序列字典序更小的行程
- **结果展示**：每段行程的班次、到发时间，以及换乘等待时间；找不到可乘行程时明确提示
- **单站站台分配**：在“站台分配”卡片选择站点与站台数量（1～4），为经过该站的每次停靠分配站台
  - 每次停靠占用 `[到达-5 分钟, 发车+5 分钟)`；首站取发车时间、末站取到达时间，区间左闭右开，按实际日期计算（跨午夜自然处理）
  - 同一站台的占用不得重叠，端点相接可共用
  - 可选**预锁**：按班次 ID 与从 0 起的停靠序号，把某次停靠锁定到指定站台；预锁必须保留，无效锁定（班次不存在、序号越界、站台越界、该停靠不在此站、重复预锁）报错
  - 停靠按（占用开始时间、班次 ID、停靠序号）排序分配；多种完整方案取站台编号序列字典序最小者；无解时明确提示
  - 单站停靠超过 20 次时报错
- **单线区间冲突排查**：在“单线区间冲突排查”卡片选择当前时刻表中有直接相邻停靠的两个站点（任一方向），输入 0～30 分钟清空间隔后排查
  - 每次区间通过占用 `[发车, 到达]`，按完整日期判断（跨午夜自然处理，同钟点不同日期不算冲突）
  - 不同班次的两次通过，占用重叠或前车驶离后未满清空间隔即冲突；恰好满足间隔不算冲突；同一班次多次通过不与自身冲突
  - 单次最多分析 20 次区间通过，超限报错
  - 返回每对冲突的班次 ID、起点停靠序号、方向与占用起止时间，并给出**需暂缓调整的最少班次集合**：同一班次多次通过整体暂缓；同样最少时取排序后班次 ID 序列字典序最小者；无冲突时集合为空
  - 分析为只读操作，不修改时刻表
- **车底接续规划**：在“车底接续规划”卡片勾选当前时刻表中 1～60 个不重复班次、填写 1～120 分钟整备时间后生成方案
  - 每个班次以首站发车至末站到达为完整任务；一组车底执行一条按时间顺序的班次链
  - 仅当**前班终站等于后班首站**、且**后班发车不早于前班到达 + 整备分钟数**时方可接续（端点相接允许，**不允许空驶**，按完整日期计算，跨午夜自然处理）
  - 每班恰好执行一次；首班前不限制车底来源（每个链首即新增一组车底）
  - 目标按字典序：**先最少化车底组数，再最小化接续等待分钟数总和**（等待 = 后班发车 − 前班到达，含整备时间）；并列最优返回任一方案
  - 返回最少组数、等待总分钟数及各车底链的班次顺序与每段接续等待；60 班次在 10 秒内算完；无效或超限输入返回 400
  - 分析为只读操作，不修改时刻表
- **限座旅客疏运测算**：在“限座旅客疏运测算”卡片选择起终站、最早出发与最晚到达时刻，勾选 1～60 个现有班次并为每班填写 1～10000 的整数席位数（所选班次总停靠数不超过 300）
  - 只使用所勾选的班次；每个相邻停靠区段的乘车人数不得超过该班席位数，旅客下车后席位即可被后续区段复用
  - 同班次只能沿后续停靠点前进、经停无需换乘时间；换车须满足换乘站最短换乘分钟数（后班发车 ≥ 前班到达 + 换乘分钟，端点相接允许）
  - 首班发车不早于最早出发时刻、末次到达不晚于最晚到达时刻，按完整日期比较，跨午夜自然处理
  - 用时间展开网络上的整数最大流（Dinic）计算时间窗内最多可送达人数，旅客可分走多条行程；再把最大流分解为带整数人数的具体行程
  - 返回最大人数及各行程的整数人数、班次、上下车停靠序号（从 0 起）与到发时间；并列最优方案任选其一；时间窗内无路时最多人数为 0
  - 班次或席位数非法、班次数量或总停靠数超限、时间格式错误或 earliest 不早于 deadline 时返回 400；测算为只读操作，不写库
- **区间延误传播排程**：在“区间延误传播排程”卡片勾选 1～40 个现有班次（所选班次总停靠数不超过 200），为晚点班次填写 0～120 分钟首发延误（未填按 0），并填写 0～30 分钟区间清空时间
  - 各班首发不得早于原时刻 + 指定首发延误，其余各站到发不得早于原时刻；区间运行时长不变（调整后到达 = 调整后发车 + 原运行时长），站内停留不少于原定时长
  - 相邻站点的无向站对视为同一单线区间；区间内各次通过的顺序按（原定发车时间、班次 ID、起点停靠序号）固定，不随延误改变；顺序相邻且属于不同班次的两次通过须满足**后车发车 ≥ 前车到达 + 清空时间**（同一班次的连续通过不自我约束，与区间冲突排查一致）
  - 全部约束均为下界，按（原发车时刻、班次 ID、停靠序号）的拓扑序一次传播即得**所有到发时刻逐项最早**的可行排程
  - 按完整日期返回每班调整后停靠时间（含原定时刻对照）与末到延误分钟数，页面并列展示原定与调整时刻、标出被推迟的时刻与末到延误
  - 班次、首发延误或清空时间非法，或班次数量、总停靠数超限时返回 400；排程为只读操作，不修改时刻表
- **晚点来源追踪**：在“区间延误传播排程”卡片点击“查看归因”（与排程同一输入：班次、首发延误、清空间隔），对每个末到晚于原时刻的班次给出末到延误分钟数、造成当前末到时刻的**全部根源**及每个根源的**一条传导链**
  - 根源只有两类：**起作用的首发延误**（首发下界恰好等于排程时刻），以及**区间冲突**（原时刻表本就违反所填清空间隔：顺序相邻的两次不同班次通过中，后车原发车早于前车原到达 + 清空间隔，且该清空约束在本次排程中取等；缺口按原定时刻计算）
  - 从末到时刻沿班内运行、站内停留、区间清空约束回溯，区间顺序沿用排程的固定顺序；**只回溯下界恰好等于本次排程时刻的约束**；多个约束并列（下界同时取等）时全部回溯、保留全部根源
  - 区间清空约束取等时**分别判断**原表冲突（按原定时刻）与前车调整后的晚点：前车晚点则继续向前车回溯其根源，原表违反清空则并记区间冲突根源，两者可同时成立、并列返回
  - 传导链从根源连到末到，每步标明班次、停靠序号、事件（发车/到达）、约束类型与完整日期时刻；无晚点的班次根源为空
  - 分析为只读操作，不修改时刻表
- **时刻表历史版本与恢复**：页面“时刻表历史版本”卡片列出全部版本（版本号、生成时间、站点数、班次数），并标明当前版本
  - 现有库首次启动时，已有的时刻表自动登记为首个版本；此后每次**成功导入**都保存一份不可变完整快照并分配递增版本号，导入失败不产生版本
  - 误导入格式合法但内容不合适的时刻表后，点击旧版的“恢复此版本”即可找回：恢复在单个 SQLite 事务内把所选快照另存为新版本并设为当前，旧版仍可再次恢复
  - 恢复请求携带页面读取时的当前版本号 `expected_version` 作乐观锁；若当前版本已被他人改动则返回 409、数据不变
  - 恢复后行程查询与站台分配立即使用恢复后的时刻表；版本记录持久化在 SQLite 卷中，重启不丢失

## 时刻表 JSON 格式

```json
{
  "stations": [
    {"id": "BJS", "name": "北京", "transfer_minutes": 10}
  ],
  "trains": [
    {
      "id": "G101",
      "stops": [
        {"station": "BJS", "arrive": null, "depart": "2026-10-01T08:00"},
        {"station": "JNZ", "arrive": "2026-10-01T10:00", "depart": "2026-10-01T10:05"},
        {"station": "SHH", "arrive": "2026-10-01T13:30", "depart": null}
      ]
    }
  ]
}
```

- `stations[].id`：站点 ID（必填、唯一）；`transfer_minutes`：本站最短换乘分钟数（非负整数）；`name`：可选显示名。
- `trains[].id`：班次 ID（必填、唯一）；`stops`：按顺序至少 2 个停靠点。
- 每个停靠点：`station` 必须引用已定义站点；首站只有 `depart`，末站只有 `arrive`，中间站两者都有；时间格式 `YYYY-MM-DDTHH:MM`。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/timetable` | 当前时刻表（站点、班次、导入时间） |
| GET | `/api/sample` | 示例时刻表 JSON |
| POST | `/api/import` | 导入时刻表（请求体为时刻表 JSON），校验失败返回 400 且保留旧表 |
| POST | `/api/query` | 查询行程：`{"origin": "BJS", "destination": "HZH", "earliest": "2026-10-01T08:00"}` |
| POST | `/api/platform-plan` | 单站站台分配：`{"station_id": "JNZ", "platform_count": 2, "locks": [{"train_id": "G101", "stop_index": 2, "platform": 1}]}`（`locks` 可选） |
| POST | `/api/section-conflicts` | 单线区间冲突排查：`{"station_a": "TJP", "station_b": "JNZ", "clearance_minutes": 10}` |
| POST | `/api/rolling-stock-plan` | 车底接续规划：`{"train_ids": ["G101", "D305"], "turnaround_minutes": 30}`；返回最少车底组数、等待总分钟数与各接续链 |
| POST | `/api/passenger-flow` | 限座旅客疏运测算：`{"origin": "BJS", "destination": "SHH", "earliest": "2026-10-01T08:00", "deadline": "2026-10-01T20:00", "capacities": {"G101": 100, "G203": 200}}`；`capacities` 为班次 ID 到席位数（1～10000 整数）的映射，须选 1～60 个班次且总停靠数 ≤ 300；返回最大人数 `total` 与各行程 `itineraries`（人数、班次、上下车停靠序号与到发时间），无路时 `total` 为 0；非法或超限请求返回 400，测算不写库 |
| POST | `/api/delay-plan` | 区间延误传播排程：`{"train_ids": ["G101", "D305"], "initial_delays": {"G101": 20}, "clearance_minutes": 10}`；`initial_delays` 为班次 ID 到首发延误分钟数（0～120 整数）的映射，未列班次按 0，须选 1～40 个班次且总停靠数 ≤ 200，清空时间 0～30 分钟；返回每班调整后停靠时间与末到延误；非法或超限请求返回 400，排程不写库 |
| POST | `/api/delay-attribution` | 晚点来源追踪：请求体与 `/api/delay-plan` 完全相同；对每个末到晚于原时刻的班次返回末到延误分钟数、全部根源（`initial_delay` 首发延误 / `section_conflict` 区间冲突）及每个根源的一条传导链（`chain`，每步含班次、停靠序号、事件、约束类型与完整日期时刻）；无晚点班次 `roots` 为空；非法或超限请求返回 400，分析不写库 |
| GET | `/api/timetable-versions` | 时刻表版本列表：`{"current_version": 2, "versions": [{"version": 1, "created_at": "...", "stations": 3, "trains": 2, "is_current": false}, ...]}` |
| POST | `/api/timetable-versions/{version}/restore` | 恢复旧版：`{"expected_version": 2}`；成功时把快照另存为新版本并设为当前，返回 `{"ok": true, "restored_from": 1, "version": 3, ...}`；当前版本与 `expected_version` 不一致时返回 409（数据不变），版本不存在返回 404 |

页面“**时刻表历史版本**”卡片即恢复入口：每个非当前版本旁有“恢复此版本”按钮，点击后确认即可。

查询成功时返回每段的到发时间与等待分钟数；找不到时返回 `{"found": false, "message": "..."}`。

站台分配成功时返回 `{"feasible": true, "assignments": [...]}`，每项含班次、停靠序号、站台号与占用起止时间；无解时返回 `{"feasible": false, "message": "..."}`；输入或预锁无效返回 400。

区间冲突排查成功时返回 `{"ok": true, "passage_count": N, "conflicts": [...], "suspended": [...]}`：每对冲突含双方通过的班次 ID、起点停靠序号、方向与占用起止时间；`suspended` 为建议暂缓的最少班次 ID 列表（无冲突时为空数组）；两站不相邻、清空间隔越界或区间通过超过 20 次时返回 400。页面“**单线区间冲突排查**”卡片即入口：下拉框只列出当前时刻表中有直接相邻停靠的站点对，选择区间与清空间隔后点击“排查冲突”即可。

车底接续规划成功时返回 `{"ok": true, "train_count": N, "turnaround_minutes": 30, "group_count": G, "total_wait_minutes": W, "chains": [...]}`：每条链 `chains[k]` 含按执行顺序排列的 `trains`（班次 ID、首/末站与到发时间）和长度为班次数 − 1 的 `connections`（`from_train`、`to_train`、`wait_minutes`）；链按首班发车时间排序。所选班次不是 1～60 个不重复班次、班次不存在，或整备分钟数不是 1～120 的整数时返回 400。页面“**车底接续规划**”卡片即入口：勾选班次（提供“全选（前 60 个）/清空选择”）、填写整备分钟数后点击“生成接续方案”，结果按车底链逐组展示班次与接续等待。

限座旅客疏运测算成功时返回 `{"ok": true, "origin": ..., "destination": ..., "earliest": ..., "deadline": ..., "total": N, "itineraries": [...]}`：每条行程含整数人数 `people`、首班发车 `depart`、末次到达 `arrive`、换乘次数 `transfers`，以及按顺序排列的乘坐段 `segments`（`train_id`、`board_index`/`alight_index` 为从 0 起的上下车停靠序号、`from`/`to` 站点与到发时间）；各行程人数之和等于 `total`，每个相邻停靠区段的合计人数不超过该班席位。时间窗内无路时以 HTTP 200 返回 `{"total": 0, "itineraries": []}`。页面“**限座旅客疏运测算**”卡片即入口，地址为 **http://localhost:8000** ：勾选班次并逐班填写席位数（提供“全选（前 60 个）/清空选择”，页面实时显示已选班次数与总停靠数），选择时间窗后点击“开始测算”，结果按行程分组展示人数、换乘次数与每段乘车的班次、停靠序号和到发时间。

区间延误传播排程成功时返回 `{"ok": true, "clearance_minutes": C, "train_count": N, "total_stops": S, "trains": [...]}`：每班含 `train_id`、`initial_delay_minutes`（首发延误）、`final_delay_minutes`（末到延误分钟数）与 `stops`——每个停靠点给出 `station`、调整后的 `arrive`/`depart` 以及对照用的 `original_arrive`/`original_depart`（均为 `YYYY-MM-DDTHH:MM` 完整日期时刻，首站无到达、末站无发车）；班次按时刻表顺序返回。调整后时刻满足：首发不早于原时刻 + 首发延误、其余到发不早于原时刻、区间运行时长不变、站内停留不少于原定时长，且同一单线区间（相邻站点的无向站对）内按（原定发车时间、班次 ID、起点停靠序号）固定的通过顺序中，不同班次的相邻两次通过满足后车发车 ≥ 前车到达 + 清空时间；返回的是所有到发时刻逐项最早的可行排程。班次数量不是 1～40、总停靠数超过 200、班次不存在或重复、首发延误不是 0～120 的整数、`initial_delays` 含未选择班次，或清空时间不是 0～30 的整数时返回 400；排程为只读操作，不修改时刻表。页面“**区间延误传播排程**”卡片即入口：勾选班次并逐班填写首发延误（提供“全选（前 40 个）/清空选择”，页面实时显示已选班次数与总停靠数），填写区间清空时间后点击“生成排程”，结果按班次展示原定与调整时刻对照表，被推迟的时刻与末到延误以醒目样式标出。

晚点来源追踪成功时返回 `{"ok": true, "clearance_minutes": C, "train_count": N, "total_stops": S, "trains": [...]}`：每班含 `train_id`、`initial_delay_minutes`、`final_delay_minutes`、`original_final_arrive`/`final_arrive`（末到原定与调整时刻）与 `roots` 根源列表（无晚点时为空）。每个根源含 `type` 与一条 `chain` 传导链：`type` 为 `initial_delay` 时给出 `train_id`、`delay_minutes`、`original_depart`/`adjusted_depart`；为 `section_conflict` 时给出 `section`（区间站对）、`clearance_minutes`、`shortfall_minutes`（原时刻表违反清空间隔的缺口分钟数，按原定时刻计算）与 `ahead`/`follow` 两次通过的班次、停靠序号、方向与到发时刻（`ahead` 同时给出原定与调整到发时刻，前车本次晚点时页面标注晚点而非正点）。`chain` 从根源连到末到，每步含 `train_id`、`stop_index`、`station`、`event`（`depart`/`arrive`）、`constraint`（`initial_delay`/`section_conflict`/`run`/`dwell`/`clearance`，即首发延误/区间冲突/班内运行/站内停留/区间清空）与 `time`（完整日期时刻）。回溯只沿下界恰好等于本次排程时刻的约束进行；清空约束取等时分别判断原表冲突（按原定时刻）与前车调整后的晚点，两者可同时成立，并列约束的全部根源都保留；校验规则与 `/api/delay-plan` 一致，分析为只读操作，不修改时刻表。入口同在“**区间延误传播排程**”卡片：排程结果摘要与表单按钮区均有“**查看归因**”，点击即按当前所填班次、首发延误与清空间隔发起归因，结果展示在排程结果下方。

## 项目结构

```
app.py                  # Flask 应用：API、SQLite 存取
planner.py              # 时刻表校验 + 最早到达搜索（Dijkstra，字典序标号）+ 单站站台分配（重叠数预检 + 记忆化回溯）+ 单线区间冲突排查（冲突图最小点覆盖）+ 车底接续规划（DAG 最小路径覆盖 = 最小费用最大二部匹配）+ 限座旅客疏运测算（时间展开网络 Dinic 最大流 + 流分解）+ 区间延误传播排程（下界约束按拓扑序一次传播求逐项最早排程）+ 晚点来源追踪（沿取等下界约束回溯根源与传导链）
static/                 # 原生 JS 前端（index.html / app.js / style.css）
sample_data/timetable.json
tests/                  # pytest：校验、搜索、站台分配、区间冲突、车底接续规划、限座旅客疏运测算、区间延误传播排程、晚点来源追踪、API（含“导入失败保留旧表”）
Dockerfile / docker-compose.yml
```
